LEVEL 1

Recording Session

Does the cycle belong to a valid, continuous recording?
▶1.1  Session boundary — gap splitgap > 3600 s → new sessionIMPLEMENTED · PROVISIONAL
Rule

If the time gap between two consecutive position samples exceeds 3600 s (1 h), a new recording session starts. Cycle detection never runs across a session boundary.

Why

Long interruptions (minutes to days were observed) separate independent recording periods — detecting a "cycle" spanning a machine shutdown would be meaningless. Typical sampling interval is ~50 ms, so 1 h is far outside normal behaviour.

▶1.2  Minimum session sizecycles per session ≥ N (TBD)PROPOSED
Rule (proposed)

A session must contain at least N complete cycles (suggestion: N = 100, to be agreed with the test engineers) for its cycles to be pool candidates.

Why

Very short sessions are typically commissioning runs, aborted experiments or start-up fragments. Their cycles are not representative of steady operation and would distort baseline statistics used for anomaly detection.

LEVEL 2

True Cycle — Standstill & Outlier Exclusion

Is this a real, complete actuator stroke — not noise, standstill or a fragment?
▶2.1  Cycle boundary detectionposition crosses 1.0IMPLEMENTED · PROVISIONAL
Rule

A cycle starts when the position signal crosses from ≤ 1.0 to > 1.0 and ends at the first crossing back to ≤ 1.0. Incomplete cycles at the window edges are discarded.

Why

The industrial supervisors confirmed the actuator is position-controlled and follows a predefined trajectory — position is therefore the most reliable reference signal (ADR-007). The threshold value 1.0 itself, however, is an unjustified magic number, duplicated in three places.

Source in repository
src/preprocessing/cycle_detection.py : line 56 movement_threshold: float = 1.0 (default) src/preprocessing/cycle_detection.py : line 74 is_moving = value > movement_threshold src/pipeline.py : line 108 config field movement_threshold = 1.0 configs/example_pipeline.yaml movement_threshold: 1.0 docs/architecture_decisions.md ADR-007 (position as reference — justified)
Evidence
Position values at rest: observed minimum_position ranges from -2.49 (sensor noise/overshoot below zero) up to exactly 1.00 (by construction of this check), P99 = 0.97 (4,601,218 cycles, outputs/.../cycles/cycles.csv). 1.0 sits just above the rest band — it works, but the margin is narrow and undocumented, and the negative outliers show real sensor noise exists.
Open point
Justify the threshold from the position-value distribution at rest (e.g. rest-band P99 + safety margin) and keep it defined in one place. As-is, a noise spike > 1.0 would count as a "cycle" — this is what checks 2.2–2.5 catch.
NO → no cycle detected (signal at rest)
▶2.2  Plausible cycle duration3.00 s ≤ duration ≤ 3.20 sPROPOSED
Rule (proposed)

Cycle duration must lie within [3.00 s, 3.20 s] (empirical P1–P99 band ± safety margin).

Why

The actuator follows a fixed trajectory, so valid cycles have a near-constant duration. Deviations indicate partial strokes, merged cycles, standstill within the cycle, or acquisition problems. Currently no duration filter exists — outliers pass unnoticed.

Evidence (n = 4,601,218 cycles)
From outputs/D63_Nr7_8/Versuch1/cycles/cycles.csv, column duration_seconds:
median 3.103 s  |  P1 3.067 s  |  P99 3.153 s  |  min 0.001 s  |  max 1551.2 s (25.9 min!)
99.96% of all cycles (4,599,230 / 4,601,218) already fall inside [3.00, 3.20] s — but 1,988 don't, including 1,473 cycles longer than 6 s, up to the 25.9-minute maximum. That outlier alone proves the filter is needed.

▶2.3  Full stroke reachedmax_pos ≥ 84.0 ∧ min_pos ≤ 1.0PROPOSED
Rule (proposed)

The cycle must reach the full commanded stroke: maximum_position ≥ 84.0 and return to rest: minimum_position ≤ 1.0.

Why

A position-controlled actuator that does not reach its target either aborted the stroke or the sensor mis-measured. Both cases must not enter a "normal behaviour" pool.

Evidence (n = 4,601,218 cycles)
maximum_position: P1 = 85.007, but the true minimum observed is only 1.05 — some cycles never really move (degenerate/failed strokes). The 84.0 threshold cleanly separates real full strokes (clustered near 85) from these degenerate ones. minimum_position: max observed 1.00 (≤ 1.0 by construction of check 2.1).

▶2.4  Expected sample count (reference signal)60 ≤ samples ≤ 66PROPOSED
Rule (proposed)

The position signal must contain 60–66 samples within the cycle.

Why

At ~50 ms sampling and ~3.1 s duration, ~62 samples are physically expected. Too few samples ⇒ data loss during the cycle; too many ⇒ duplicated timestamps or merged cycles.

Evidence (n = 4,601,218 cycles)
number_of_samples: P1 = 62, median 63, P99 = 64 — but the true range is 2 to 30,966 samples (source: outputs/.../cycles.csv). The 30,966 outlier is almost 500× the normal count — clearly a timestamp/merge artifact, not a real cycle. Band [60, 66] adds tolerance of ±2 samples around the typical value.

▶2.5  Standstill / frozen-signal checkΔpos > δ within window T, or |v| > εPROPOSED
Rule (proposed) — the explicit standstill definition

Within a detected cycle, the actuator must actually be moving: the position must change by more than δ within every rolling window of length T (suggestion: δ = 0.5 position units, T = 0.5 s), or equivalently the velocity signal must satisfy |v| > ε during the motion phases. A cycle that stays flat > T is standstill or a frozen sensor.

Why

Standstill between cycles is already excluded by check 2.1 (position at rest ≤ 1.0 detects no cycle). The remaining risk is a frozen position signal stuck above 1.0 (sensor fault, communication freeze), which would currently be counted as a valid cycle. The velocity signal is extracted but never used anywhere in the current pipeline — this check puts it to use.

Source in repository
— not implemented — no standstill detection exists in the codebase velocity is extracted but unused: configs/example_pipeline.yaml selected_extraction_signals: velocity src/preprocessing/multi_sensor_cycle_extraction.py known limitation "velocity scaling unverified": docs/implementation_log.md section "Current Limitations"
Open point
δ, T and ε are placeholders — derive from position/velocity distributions. Blocker for the velocity variant: the physical scaling of the velocity signal is not yet verified (docs/implementation_log.md). Until then, use the position-based variant.
NO → reject cycle: standstill / frozen signal

LEVEL 3

Multi-Sensor Completeness

Are all required sensor signals present with enough samples?
▶3.1  All required signals present8 / 8 signals existIMPLEMENTED · JUSTIFIED
Rule

All configured required signals must exist (non-empty) within the cycle interval: position, velocity, current, pressure, temperature, vibration_x, vibration_y, vibration_z. Missing data is never interpolated or filled.

Why

Each pool cycle becomes one ML training sample containing all sensors (ADR-010). A cycle with missing channels would create an inconsistent feature vector. Sensor availability is known to differ between recording periods, so this check is essential.

▶3.2  Minimum samples per signalper-signal sample_count ≥ minIMPLEMENTED · PROVISIONAL
Rule

Each required signal must reach its configured minimum sample count. Current config: position/velocity/current/vibration ≥ 20, pressure/temperature ≥ 1 — values are configured but nowhere justified.

Proposed data-driven update

Tighten to the observed distributions: position / velocity / current ≥ 60 (observed: exactly 63), pressure ≥ 45 (observed: 51–52), vibration_x/y/z ≥ 1100 (observed: 1251–1269), temperature ≥ 2 (observed: 3). The current minimum of 20 would accept a cycle that lost two thirds of its position samples.

LEVEL 4

Per-Signal Quality

Is each signal internally healthy within the cycle?
▶4.1  Signal coverage of the cyclecoverage_ratio ≥ 0.9 (TBD)AWAITING DATA
Rule (proposed)

Each signal's samples must span at least 90% of the cycle duration (coverage_ratio = duration_covered / cycle_duration). Threshold to be finalized from Stage-8 distributions.

Why

A signal can pass the sample-count check yet cluster all samples in one half of the cycle, leaving the other half blind. Coverage catches partial signal dropouts within a cycle.

▶4.2  No large gaps inside the cyclemax_time_gap ≤ TBDAWAITING DATA
Rule (proposed)

The largest gap between consecutive samples of a signal within the cycle must not exceed a signal-specific threshold (e.g. a multiple of the signal's median sampling interval; position: ~50 ms nominal).

Why

Supervisors confirmed small timestamp jitter (43–58 ms for position) is normal, but larger intra-cycle gaps mean lost measurements exactly where the dynamics happen.

▶4.3  No invalid valuesnon_finite_count = 0AWAITING DATA
Rule (proposed)

No signal may contain NaN or ±infinity values within the cycle.

Why

Non-finite values break feature computation (FFT, RMS, correlations) silently or catastrophically. Zero tolerance is the only defensible threshold here — this one needs no distribution to justify.

▶4.4  Signal not frozen / constantstd_value > 0 (dynamic signals)AWAITING DATA
Rule (proposed)

Dynamic signals (position, velocity, current, pressure, vibration) must show variation within the cycle: std_value > 0 (or above a small signal-specific floor). Temperature is exempt — 3 samples per cycle may legitimately be near-constant.

Why

A perfectly constant "dynamic" signal indicates a frozen sensor or a stuck acquisition buffer — the multi-sensor complement to the standstill check 2.5.
