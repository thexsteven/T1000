Which measurement data can we use?

The decision tree in plain language — this explains how our quality control works for the electric actuator test data.

What is this about?

Our actuator moves back and forth continuously in the experiment. One round trip is called a cycle — it takes about 3 seconds. Eight sensors record data during each cycle: position, velocity, current, pressure, temperature, and vibration in three directions.

Later, a dashboard should show the test engineers each day whether the actuator behaves normally. The system must learn what "normal" looks like. If we give it bad data, it learns the wrong thing — and later it will raise false alarms or miss real problems.

That is why we check each cycle at 4 stations — like a quality control line. Only cycles that pass all 4 checks enter the usable data pool.

1

Does the cycle come from a real recording session?

Was the recording continuous?

The system does not record continuously. There are pauses — overnight, on weekends, during maintenance. If more than one hour passes between two recorded values, we treat that as the end of one session and the start of a new one.

Also: very short recording sessions with only a few cycles (for example, a quick setup run) are not representative of steady operation.

Example: The system stops at 4 pm on Friday and resumes at 8 am on Monday. Without this separation, the system would think one cycle lasted the entire weekend.
✗ Rejected: data from recording gaps and too-short setup runs.
passed ✓
2

Is this really a complete, proper stroke?

Did the actuator move normally?

Here we filter out everything that only looks like a cycle. From over 4.6 million detected raw cycles, we know very well what a normal stroke looks like — and we compare every new cycle against that.

A real stroke lasts about 3.1 seconds (our tolerance: 3.0 to 3.2). The carriage must reach the front and return completely — no half-strokes. And the sensors must deliver the expected number of samples.

We also check for standstill: if the position does not change for a longer time while the cycle is supposed to be moving, the sensor is probably frozen — the values are stuck.

Example: In our data we found one "cycle" lasting over 25 minutes (1,551 seconds) — more than 500× longer than normal. That is clearly not a normal stroke and should not be used as an example of "normal".
✗ Rejected: aborted strokes, merged double cycles, standstill, frozen sensors, noisy signals.
passed ✓
3

Did all 8 sensors record?

Is the data set complete?

For the analysis we need data from all 8 sensors for every cycle — and enough samples from each sensor. From experience we know that some sensors sometimes fail or record incomplete data.

A cycle that is missing, for example, vibration data is unusable for comparison — it would be like comparing cars while one of them has no speedometer. Important: we do not invent missing values. If something is missing, it stays missing — and the cycle is rejected.

Example: A vibration sensor normally delivers over 1,200 samples per cycle. If only 300 arrive, the recording failed.
✗ Rejected: cycles with missing sensors or too few samples.
passed ✓
4

Are the measurements themselves okay?

Deep check of each signal

Finally, we look inside each sensor individually. Four things are checked:

Does the signal cover the whole cycle? Not just the first half. — Are there gaps in the middle of the stroke? That is exactly where the important motion happens. — Are all values valid numbers? No transmission errors. — Is the signal alive? A vibration signal that is a straight line during the stroke is broken.

Note: The exact thresholds for this station are being derived from the available measurement data — that requires the full thesis run to complete. The quality metrics themselves are already implemented.
✗ Rejected: cycles with signal dropouts, invalid values, or broken sensors.
all 4 stations passed ✓
✓

The data pool

Only these reviewed cycles are used further: for the visualization where cycles are stacked and compared, and as the training basis for automated anomaly detection. Rejected cycles are not deleted — each one keeps its rejection reason. This is always traceable.

The three key messages for the discussion

  • Quality before quantity: Better fewer, reliable cycles in the pool — otherwise the anomaly detector learns "normal" from bad data.
  • Nothing is arbitrary: The thresholds (for example 3.0–3.2 seconds) are based on the statistics of over 4.6 million real cycles — not on gut feeling.
  • Everything is traceable: Every rejected cycle keeps its rejection reason. Every rule is documented and can be adjusted with the experts.
