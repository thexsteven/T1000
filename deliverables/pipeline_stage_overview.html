ERA Preprocessing Pipeline — Visual Stage Reference

Companion to the Confluence page “Data Preprocessing — Criteria Maturity & Alignment Overview.” Every stage below is cross-checked between Fatemeh’s pipeline code (/home/ita/MasterThesis) and the overview wording. Where they disagree, both are shown and flagged.

Last updated: 2026-07-22 · Based on: Fatemeh Heydari, docs/thesis_pipeline.md — Preprocessing Pipeline V2.1 (2026-07-22)
Bottom line: the mechanisms — why have a threshold at all, why separate sessions, why use a robust statistic — are consistently well justified. The pipeline now performs statistical validation and cycle rejection itself (Stage 10). The two segmentation values that remain provisional (3600 s, Position > 1.0) are what the t1000 physical-plausibility layer re-derives from data; the learned statistical bounds (MAD limit 3.5) belong to Fatemeh's Stage 9.

Status tag legend

Justified — physically or methodologically grounded (e.g. via ADR)
Provisional — actively used, but not physically/methodologically derived
Structural — enforced by pipeline logic, but not physically validated
Statistically derived (not health-validated) — threshold generated from the observed data distribution (Median + MAD, quantile fallback), but the reference population has not been confirmed to represent healthy behaviour
Inconsistent — conflicting sources disagree on status/value
Unjustified — no documented reasoning exists
Planned / Not implemented — stage does not yet exist in code

Justified

Justified

Stage 05Recording Session Detection

Justified (mechanism) Inconsistent (value)
What it doesScans the signal incrementally in record batches and splits the full recording history into sessions wherever the gap between consecutive timestamps exceeds the threshold.
JustificationThe mechanism prevents joining data across shutdowns/maintenance — but the concrete 3600 s value is not justified, only the approach. Re-derived from data by the t1000 layer.
session_gap_seconds: 3600.0 s (1 h) code default DEFAULT_SESSION_GAP_SECONDS = 3600.0 Source: session_detection.py · ADR-006 · thesis_pipeline.md Stage 5
⚠ discrepancy Mechanism vs. value: code hard-codes the 3600 s default (config-overridable via session_gap_seconds), and ADR-006 accepts the 1-hour approach “based on the empirical timestamp analysis” — but neither the ADR nor the code derives why 3600 s specifically. Mechanism is justified; the numeric value is flagged inconsistent.

Stage 06Position-Based Cycle Detection

Justified (signal) Provisional (threshold)
What it doesDetects candidate cycles on the Position signal: a cycle starts when the value crosses from ≤ threshold to > threshold and ends on the reverse crossing; incomplete cycles at the window edges are dropped.
JustificationThe actuator is position-controlled, so the reference-signal choice is justified (ADR-007) — but the threshold 1.0 is explicitly provisional, with no physical derivation. Re-derived from data by the t1000 layer.
movement_threshold: 1.0 → Position > 1.0 code default movement_threshold = 1.0 Source: cycle_detection.py · thesis_pipeline.md Stage 6
⚠ discrepancy Typical cycle duration: the Implementation Log §8 reports a typical cycle duration of ~3.1 s, whereas an older project-context figure assumed a 1.81 s round-trip. Both are shown; this reference explicitly does not resolve which is correct.

Stage 07Multi-Sensor Cycle Extraction

Justified
What it doesFor each detected cycle interval, slices every available experiment signal (position, velocity, current, pressure, temperature, vibration x/y/z) into per-cycle windows at their native sampling rates, using a session-level signal cache. Never rejects a cycle because an optional signal (vibration) is absent.
JustificationNo resampling/interpolation is applied because sensors have different native sampling frequencies (ADR-008). Duty-cycled ESP32 vibration is legitimately absent from most cycles — an absent optional signal never fails extraction.
native rate · no resampling Source: thesis_pipeline.md Stage 7 (Multi-Sensor Extraction) · ADR-008

Stage 08Cycle Quality Profiling

Justified
What it doesComputes purely descriptive per-cycle and per-signal quality metrics (sample counts, coverage ratio, stroke range, sampling-interval statistics, constant-signal / non-finite counts). It records but does not reject any cycle.
JustificationDeliberately non-rejecting — this prevents arbitrary early filtering and keeps the later rule generation fully traceable to the observed population.
descriptive only · no pass/fail Source: cycle_quality_profiler.py · thesis_pipeline.md Stage 8

Stage 09Validation Rule Generation

Statistically derived (not health-validated)
What it doesLearns per-signal validation bounds from the profiled cycle population before any rejection: robust Median + MAD z-score bounds by default (robust_z = 0.6745·(x−median)/MAD), falling back to quantile bounds when MAD is zero or degenerate. Separates hard rules (logical/domain) from learned rules; marks rules provisional when the reference population is limited.
JustificationMedian + MAD is a robust statistic and the quantile fallback covers instability — statistically justified, but the reference population is not verified as healthy.
default_method: median_mad mad_z_limit: 3.5 fallback: quantile 0.01 / 0.99 reference: all_profiled_cycles (vibration: vibration_complete subset)
Source: validation_rule_generation.py · validation_thresholds.json · thesis_pipeline.md Stage 9

Stage 10Dataset Validation

Justified (core logic) Structural (vibration) Unjustified (reference pop.)
What it doesThe only pipeline stage that rejects cycles. Applies the frozen Stage-9 rules to every profiled cycle and assigns a final class — valid_core_cycle, valid_complete_multisensor_cycle or invalid_cycle — with reason codes. Absence of duty-cycled vibration alone never invalidates a core cycle.
JustificationVibration is treated as optional not mandatory (core vs. supplementary signals) — cleanly justified. But rules are applied against all_profiled_cycles, with no explicit healthy-subset selection.
core_required vs. optional_duty_cycled (vibration x/y/z) reference_population: all_profiled_cycles
Source: dataset_validation.py · thesis_pipeline.md Stage 10
⚠ open gap Reference population: validation runs against all_profiled_cycles with no documented healthy-subset selection — so the population underlying the learned thresholds is unjustified as a health baseline, even though the core validation logic and optional-vibration handling are sound. This is exactly the gap the t1000 physical floor (absolute values, no healthy reference needed) is designed to cover.
